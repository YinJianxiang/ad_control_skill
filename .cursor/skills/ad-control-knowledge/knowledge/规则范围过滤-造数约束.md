# 规则范围过滤：通用造数约束

造管控条件主表时，除指标阈值外，还必须让造数行通过 Job 扫描的 **WHERE 范围过滤**。  
本知识是**跨业务线、跨用例**的通用约定：从规则字段推导事实列取值，不绑定某一条规则或某一个 case。

## 一句话

指标算对了只过 HAVING；  
规则上勾选的负责人、剧类型、主体、状态等会先拼进 WHERE。  
造数行若缺字段、为 NULL、或不在名单内 → **扫不到 → 无 HIT 日志**，看起来像「Job 没跑」或「小时对不上」。

## 总原则

1. **先读规则，再涂事实列**：凡规则字段不是「不限 / -1 / null / 空」，造数就必须落到对应事实列，且取值落在 Job 会生成的谓词里。  
2. **NULL ≠ 不限**：`col in (...)` 不会匹配 NULL/空串；缺列等同被过滤。  
3. **指标层与范围层正交**：HIT 造数要同时满足「范围 WHERE 通过」+「指标 HAVING 命中」；MISS 可故意让一层不通过以便归因。  
4. **按规则字段通用推导**，禁止为单个 case 写死互斥特例。

## 规则字段 → 事实列（WHERE）

「不限值」下列取值时，Job **不**追加该谓词，造数可不强行涂该列（仍建议骨架齐全）。

| 规则字段 | 常见不限值 | 事实列 / 行为 | 造数要求 |
|---|---|---|---|
| `channel_users` | `不限`、空 | `agent_user_name in (...)`；「本部门全部」按创建人部门解析 | 行上负责人必须落在名单内；不要用无关测试人名 |
| `drama_type` | `-1`、`不限`、空 | `drama_type in (...)` | 行上剧类型必须是名单中的一个；禁止留空 |
| `main_bodys` | `不限`、`-1`、空 | `main_body in (...)` | 主体落在名单内 |
| `video_type` | `-1`、null | `video_type = ...` | 与规则一致 |
| `opt_status` / `project_status` | `-1`、null | 小时表多在 WHERE：`project_status` / `promotion_status` 排除暂停删除或等于目标态 | 与规则开关一致（如「投放中」→ 开启/投放中，勿用暂停） |
| `bid_strategy_id` / `bid_strategy_ids` | null / `-1` | `bid_strategy_id` 等值或 in | 有指定时必须对齐 |
| `ignore_book_ids` / `effective_book_ids` | `-1` | `book_id not in` / `in` | 生效名单内；忽略名单外 |
| `ignore_channel_codes` / `ignore_accounts` | `-1` | 渠道/账户排除 | 测试渠道不要落在忽略名单 |
| `account_type` | `-1`、null | `account_type =` | 对齐 |
| `delivery_way` / `delivery_mode` / `bid_type` / `put_mode` 等 | `-1`、`不限`、空 | 对应列等值或 in（部分存中文枚举） | 按规则字面量涂，勿臆造枚举 |
| `doType=8`（ROI 更新系数） | — | Job **额外**强制 `delivery_mode='自动投放'`（非全域 releaseVer=3） | 造数行须为「自动投放」；若规则自身又配了其它投放模式，WHERE 会矛盾，需先对齐规则或无法 HIT |
| `external_action` / `deep_external_action` | `不限` / `-1` | 对应行动列 | 非不限时对齐 |
| `app_name` / `book_id` / `channel_prefix` | `-1`、`不限` | `in` 或 `LIKE` 前缀 | 测试值满足匹配 |
| `is_anime` / `anime_type` | `-1` / 不限 | 等值或 `FIND_IN_SET` | 有限制时对齐 |
| `release_ver` | `-1`、null | 部分业务线在渠道/项目维追加 `release_ver=` | 骨架与规则投放版本一致（另有 job 路由按 releaseVer 分表） |

说明：上表映射以 Job `ruleBaseCondition2Where` 为准；业务线若缺列则该谓词无效或需换表，以授权场景表结构为准。

## 小时口径：扫描窗口（HAVING 前的时间键）

近 N 小时类条件（`timeType` 为小时枚举）时：

| Job 时间键 | 含义 | 造数 `hour` |
|---|---|---|
| `nearly1Hour` | 当前自然小时 − 1 | 必须写入该小时（`HH` 零填充，如 `09`） |
| `nearly2Hour` | 当前自然小时 − 2 | 近 2 小时/窗口涉及 H2 时同样对齐 |
| `nearly3Hour` 等 | 当前自然小时 − N | 类推；越界可能为 `--`（该小时指标为 NULL） |

硬约束：

- **禁止**把用例 `fixed_defaults.hour` 写死成与执行时刻无关的常量（除非执行时刻保证一致）。  
- 造数 `cdate` 取规则日集合：纯小时条件一般为**当天**。  
- 分时比率：在目标 `hour` 上同时写齐分子、分母；Job 用 `hour = nearlyNHour` 过滤后再聚合，窗口外的行不计入该 Hn 指标。  
- 当前小时为 0 且任务判定为首批时，调度可能直接跳过；手工指定 ruleId 的测试仍要注意窗口小时是否为 `--`。

## 指标层（HAVING）仍要满足

范围通过后，才轮到条件列：

- 比率：先分别汇总分子、分母，再相除；不要只改展示用 ROI 列。  
- `anyone` / `all` / `total` / `first` 按授权场景与 Job 列前缀（如 `_data_h1_*`、`_data_d_*`）理解；造数覆盖 Job 实际取值的那些时间桶。  
- 比较符与阈值以规则为准；边界值是否命中以 Job SQL（含 NULL 语义）为准。

## 与「单书/剧数据筛选」的关系

- 本文件：主表扫描 **WHERE 范围 + 小时窗口 + 条件 HAVING**。  
- `单书剧数据筛选-造数规则.md`：筛选开启后的**书剧大盘层**。  
两层都开启时，两套约束都要满足；缺一层都会导致无最终管控结果。

## 造数检查清单（执行前）

1. 列出规则上所有非「不限」的范围字段 → 对照上表给每行涂事实列。  
2. 若存在小时条件 → 按执行时刻计算 `nearlyNHour`，写入对应 `hour` + 当天 `cdate`。  
3. 指标写列与授权公式一致；多条件同表同时间粒度。  
4. 可选：用与 Job 同构的 WHERE + HAVING 对造数渠道做一次 SQL 复现，确认能选出行，再触发 Job。

## 常见错误（禁止）

1. 只调消耗/ROI，忽略 `drama_type`、`agent_user_name` 等范围列 → WHERE 滤光。  
2. 小时条件写死错误 `hour`，导致 `_data_hN_*` 为 NULL，比较永不成立。  
3. 把「规则未限制」理解成「事实列必须为空」——空值在有 `in` 限制时反而失败。  
4. 负责人/主体/剧类型用与规则名单无关的占位值。  
5. 为本文件再拆成某个 case 私有口径，而不是按规则字段推导。

## 与用例的关系

用例声明业务线、维度、条件与可选 `fixed_defaults`。  
造数引擎/人工造数：**以运行时规则记录为准**覆盖范围列与小时窗口；用例写死的 hour/负责人若与规则或执行时刻冲突，以规则 + Job 窗口为准并覆盖用例默认值。
